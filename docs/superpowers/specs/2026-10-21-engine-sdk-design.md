# Engine SDK: граница движка и игр

Дата: 2026-10-21. Статус: согласовано пользователем и реализовано локально. Точный публичный API описан в [engine-sdk.md](../../engine-sdk.md).

## Цель и границы

Игра описывает свои действия, настройки и игровые правила и использует SDK. Движок исполняет эти декларации, выбирает компоновку, разрешает тему, управляет игровым временем, владением вводом, сохранением и восстановлением после поражения. Добавление картриджа требует регистрации в каталоге, но не изменения оболочки, формы настроек, хранилища или генератора темы.

В этом подходе мигрируют обе существующие игры. Новые игры, публикация, сетевые плагины, отдельные пользовательские циклы и переписывание приложения целиком на React не входят в работу. Существующие локальные изменения сохраняются. Ниже сохранён согласованный проект архитектуры; актуальные сигнатуры и ограничения собраны в справочнике SDK.

## Рассмотренные варианты

1. **Только исправить мобильные кнопки.** Небольшая правка, но следующие игры продолжат требовать изменения host/storage/settings. Не решает запрос.
2. **Развить текущий картридж до SDK — рекомендуется.** Оставить чистые правила/ИИ/Canvas и Session. Вынести общие адаптеры, добавить декларации, кодеки и явные контексты. Мигрировать Snake/Tetris и доказать отсутствие специальных веток тестовым картриджем.
3. **Универсальная система плагинов, сцен и произвольных виджетов.** Даёт большую свободу, но вводит второй UI-фреймворк и лишнюю сложность. Для существующих игр не требуется.

Игра не импортирует host, React/shadcn, CSS, localStorage или browser media APIs. Она может рисовать игровую геометрию через Canvas-контекст: это не знание вёрстки страницы. Жёсткий sandbox для недоверенных плагинов здесь не создаётся.

## SDK и регистрация

Одна публичная точка `engine/sdk` экспортирует типы определения игры, семантических действий, настроек, состояния и визуального контекста, а также чистые random/draw/recovery helpers. Игры не импортируют внутренние модули Session, оболочку или друг друга.

Предлагаемая структура контракта:

```ts
interface GameDefinition<State, Settings, Action extends string> {
  metadata: GameMetadata;
  settings: SettingsDefinition<Settings>;
  configure(settings: Readonly<Settings>): GameRules<State, Action>;
  persistence: StateCodec<State, Settings>;
}

interface GameRules<State, Action extends string> {
  viewport: LogicalViewport;
  tickMs: number;
  strategy: string;
  actions: readonly ActionDefinition<Action>[];
  create(seed: number): State;
  update(state: State, action: Action | null, context: StepContext): State;
  ai(state: State): Action | null;
  render(
    ctx: CanvasRenderingContext2D,
    state: State,
    frame: RenderContext,
  ): void;
  metrics(state: State): readonly Metric[];
  labels?: readonly BoardLabel[];
  recovery?: RecoveryPolicy<State>;
}
```

Это эскиз формы API; точные type aliases выводятся из реализации и проверяются TypeScript. `defineGame(...)` помогает вывести типы без повторения generic-параметров. У состояния сохраняется минимальный контракт `score`/`over`. RNG принадлежит сериализуемому состоянию конкретной игры; движок не требует поля с именем rng.

`configure` создаёт набор чистых правил/представления из нормализованных настроек, без запуска таймеров и регистрации обработчиков. Каталог содержит только определения игр; универсальный адаптер создания и обслуживания Session находится в движке. Иконка, название и описание приходят из статических метаданных, без ветвления по id игры. Подпись поля и strategy находятся в настроенном GameRules: смена стратегии Snake обновляет текст HUD вместе с правилами.

## Игровые действия отдельно от команд движка

Команды имеют разные типы:

```ts
type EngineCommand =
  | "pause"
  | "autopilot"
  | "restart"
  | "speed"
  | "settings"
  | "library"
  | "focus"
  | "help";

type Input<Action extends string> =
  | { kind: "engine"; command: EngineCommand; value?: number }
  | { kind: "game"; action: Action };
```

Игровые action-id могут быть строковым union картриджа. В первой миграции существующие up/left/down/right/primary сохраняются как id для правил и ИИ, чтобы не менять симуляцию одновременно с границами. Их расположение и представление определяются описательной ролью, а не именем id.

ActionDefinition содержит id, label, keys, role, repeat и необязательный короткий caption. role — семантика действия (`move-up`, `move-left`, `move-down`, `move-right`, `rotate`, `primary`, `secondary`), а не CSS-координаты, номер ячейки или breakpoint. Игра не передаёт JSX, размеры кнопок и обработчики DOM. Безусловные системные клавиши зарезервированы движком; повтор берётся из декларации действия. Пользовательские каналы ввода вызывают один engine dispatcher. ИИ возвращает те же action-id внутри engine tick, но не проходит ветку ручного перехвата и не меняет mode на human.

Системный набор описан один раз и порождает кнопки, hotkeys и справку. Автопилот — идемпотентная команда «вернуть ИИ», а не другое название игрового primary. Ручной режим включается игровым действием. Session не должен интерпретировать primary как рестарт: повтор партии — команда движка. Терминальная Enter-связка — контекстное исключение: она сохраняется отдельным engine-binding и имеет приоритет только после завершения партии; Enter во время Tetris остаётся заявленным hard drop. Валидатор разрешает такое разделение по взаимоисключающим контекстам, но отклоняет одновременно активные конфликты.

## Единая компоновка управления

Пауза, автопилот, рестарт и скорость всегда находятся в системной панели, в одинаковом порядке и месте для всех игр данного viewport. Их видимость не зависит от наличия primary/secondary у игры. На мобильном автопилот всегда внизу вместе с прочими системными действиями; engine Focus/Help остаются desktop-only.

Игровой pad — отдельный горизонтальный прямоугольник 2×3. Движок использует семантические роли:

| Верхний левый | Верхний центр        | Верхний правый |
| ------------- | -------------------- | -------------- |
| secondary     | move-up, либо rotate | primary        |
| move-left     | move-down            | move-right     |

Snake занимает четыре направления. Угловые ячейки остаются пустым пространством без фиктивных кнопок. Tetris занимает rotate сверху по центру, hard drop справа сверху и left/soft drop/right снизу. Пауза и ИИ **не заполняют** свободные игровые позиции. При наличии и move-up, и отдельного rotate движок помещает rotate в свободный дополнительный слот; конфликт или переполнение выявляются при регистрации, а не молча скрывают действие. Раскладка рассчитана на текущие игры и до шести показанных действий; большие наборы требуют отдельного общего расширения SDK.

В горизонтальном мобильном виде pad может стоять справа от поля; состав и позиции системной панели остаются одинаковыми для всех картриджей. Размер поля не меняется при ручном перехвате.

## Настройки: схема и жизненный цикл

General — настройки движка: theme/accent, motion и общие preferences. Скорость также принадлежит движку; состояние владения ИИ и пауза — Session, а не опции игрового картриджа.

Вкладка текущей игры строится из схемы. Минимальные поля: boolean, choice, number и группы. Общий механизм пресетов описывает патчи значений существующих полей; Snake S/M/L — такие пресеты для columns/rows. Форма не знает, почему размеры должны быть чётными: ограничения и сообщение задаёт картридж.

Схема содержит defaults/normalize для недоверенных сохранённых данных, validate для черновика и effect(previous, next). Допустимые эффекты: `none`, `presentation`, `rules`, `restart`. Для составного изменения выбирается самый сильный эффект. Переключение стратегии ИИ — игровая настройка; включение автопилота — системная команда.

Preview опции — синхронный чистый callback `preview(ctx, readonlyDraftSettings, logicalBounds, readonlyVisuals): void` рисования в выделенную движком логическую область с теми же visual tokens. Он не получает DOM, Session, функции регистрации или lifecycle hooks. Движок перерисовывает preview при изменении соответствующего черновика, resolved appearance или логических bounds. Движок владеет элементом, размером, подписью, расположением и моментом перерисовки. Это сохраняет превью скинов без импорта SnakePreview в общую форму. Не вводится возможность игры поставлять произвольный React-компонент формы.

Применение:

1. Открытие панели приостанавливает игру и запоминает прежнюю паузу. Черновик изолирован; Cancel/Escape/закрытие его отбрасывают.
2. Apply проверяет весь черновик, нормализует его на границе картриджа и вычисляет effect. Невалидный черновик не меняет игру или storage.
3. `none`: только закрыть панель, не пересоздавать правила и состояние.
4. `presentation`: оставить тот же Session, состояние, RNG, историю, активный откат, очередь и round; заменить отрисовку/подписи/preview.
5. `rules`: заменить настроенные правила и ИИ, сохранив совместимое состояние, RNG, seed, round, владение, паузу и скорость. Очистить устаревшую очередь, историю и откат. Если настройки применены во время отката, принимать **полный стабильный snapshot**, а не промежуточный проигрышный кадр: state, seed, round, mode и pause должны соответствовать друг другу. При fallback snapshot уже содержит board следующей партии и её новые seed/round — старые метаданные поверх него не сохраняются.
6. `restart`: новый совместимый board через общий lifecycle, без попытки восстановить старую геометрию. В этой миграции сохранить текущую семантику resize: текущий seed, mode и autoSpeed; новая партия с round=1 и снятой паузой. Обычный Restart по-прежнему получает новый seed. Изменение этой политики — отдельное продуктовое решение.
7. После успешного перехода сохранить настройки и сессию. General appearance меняет только presentation context и CSS; Session не пересоздаётся.

Функциональное равенство callback-ссылок не используется как описание совместимости. Политика перехода объявлена явно и покрыта тестами.

## Сохранение и совместимость

Движок проверяет размер и структуру конверта: версию, game-id, seed/round, mode, pause и допустимые speed. Игра владеет версией своего состояния и decoder/validator, а также проверкой совместимости state/settings. В storage нет импортов Snake/Tetris, проверки piece.kind, collides или columns.

Существующие ключи localStorage и сохранения v1 поддерживаются. Движок читает старый конверт, затем передаёт state соответствующему кодеку. Повреждённая или несовместимая запись отбрасывается только для этой игры. Для следующего формата envelope-version и state-version разделены; переход v1 → новый конверт выполняется при успешном чтении/сохранении без массовой очистки storage.

Сохранение во время отката продолжает записывать безопасную конечную позицию либо fallback новой партии с правильными seed/round. История отката не сериализуется. Explicit restore очищает очередь, старое время и историю. Эти существующие гарантии сохраняются.

## Визуальный SDK

Один чистый resolver движка строит CSS-токены оболочки и неизменяемый VisualTheme для каждого render/preview. В контексте есть accent, accentMuted, secondary, background/grid/text/muted, categorical palette и общие effect tokens (recovery/strong, flash/highlight/ghost opacity). reducedMotion и анимационное время также передаются явно.

- Snake связывает head с accent, body с accentMuted, food с secondary. secondary — противоположный hue с поправкой яркости/насыщенности для видимости. Для ахроматического акцента движок использует стабильный резервный hue и явно документирует эту политику.
- Tetris сопоставляет семь стабильных видов фигур семи индексам engine palette. RGB, light/dark ветки и выбор контраста — в движке. При смене темы индексы фигур не переставляются.
- Геометрия змейки, разделители, глаза, изгибы, падающие фигуры, ghost/next и выбор клеток для flash — ответственность renderer игры.
- Игра сообщает затронутые сущности/ряды и прогресс игрового события; engine helpers разрешают tint, opacity и reduced-motion поведение. В играх нет самостоятельно заданных цветов (включая named CSS colors, RGB/HSL и gradient stops), чтения CSS/media или собственных theme listeners. Все вложенные effect tokens и массив categorical также readonly.
- clear/grid и feedback helpers получают явный визуальный контекст; mutable palette/lightPalette singletons удаляются после миграции обоих renderer.
- Логические BoardLabel остаются декларациями. Оболочка рисует резкий текст и масштабирует его вместе с полем. Вёрстка и шрифт не задаются игрой. Текущее числовое BoardLabel.size заменяется семантической ролью (например caption/body); движок выбирает размер, минимальную читаемую величину и масштабирование.

Простой Canvas SDK достаточен; scene graph и собственный язык векторных примитивов не нужны. Статические иллюстрации интерфейса и типографика UI также остаются задачей движка; спрайты и игровая геометрия остаются у картриджа.

## Миграция и контроль масштаба

Последовательность областей работы, не детальный план реализации:

1. Зафиксировать контракт SDK и типы отдельных engine/game commands, перенести универсальный cartridge adapter в движок.
2. Вынести codecs/compatibility и декларации настроек в существующие картриджи; сделать каталог списком определений, а storage и settings renderer универсальными.
3. Перевести host lifecycle и ввод на общие методы; убрать ветки по game.id и смешивание системных/игровых кнопок.
4. Передать visual context, мигрировать оба renderer и previews, удалить глобальные palette/media dependencies.
5. Обновить документацию и `.agents/skills/create-zero-player-game` под фактический SDK, включая новый пример регистрации.

Не переписывать алгоритмы ИИ, поиск путей, физику и scoring в этом рефакторинге. Входные последовательности и seeded states до/после должны давать одинаковую симуляцию. Частичные адаптеры допустимы на время миграции, но финальное состояние не оставляет специальных путей для старых игр.

## Критерии приёмки

- В core/shell/storage/settings нет импортов конкретных игр и switch/if по snake/tetris. Только composition root/catalog импортирует и регистрирует определения.
- Минимальный тестовый картридж с собственными action-id, настройками и кодеком подключается без изменения host/UI/storage/theme. Это тестовая fixture, а не третья пользовательская игра.
- Декларации входа и клавиш валидируются: дубликаты, одновременно активные конфликты с engine bindings и непомещающиеся действия не исчезают молча.
- Системная панель имеет одинаковые позиции и доступность при 0/4/5/6 игровых действиях; primary/secondary не вытесняют pause/auto/restart.
- Keyboard, touch и AI используют одни игровые действия. Сохраняются физические/Russian раскладки, IME/формы/browser shortcuts, Enter/Space на нативных элементах и объявленные повторы.
- Manual всегда 1×, Auto восстанавливает сохранённый multiplier с существующим easing. Базовый tick задаёт игра. Pause/restart/recovery сохраняют текущие гарантии.
- Архитектурные проверки запрещают game imports из host/theme internals, DOM/media/storage/time API и самостоятельно заданные цвета; публичный SDK остаётся разрешённой границей.
- Presentation-only apply сохраняет точный Session и rewind history; rules apply сохраняет совместимую позицию и очищает устаревшую историю; resize не загружает прежний board.
- Кодеки обеих игр покрывают старые сохранения, corrupted input, несовместимые настройки, запрет storage и сохранение во время recovery. Rules apply во время обычного rewind и fallback проверяет соответствие полного стабильного snapshot его seed/round.
- Состояние и ИИ остаются immutable/deterministic. Длительные Snake/Tetris симуляции и существующие recovery tests проходят без изменений ожидаемых правил.
- Один state можно отрисовать с двумя VisualTheme без взаимного влияния. Все семь цветов Tetris и семантические эффекты проверяются в dark/light и крайних custom accents: существенные графические токены имеют контраст минимум 3:1 с board background, текст — 4.5:1. Render assertions подтверждают фактическое использование injected tokens обоими renderer; индексы categorical стабильны и различны.
- Смена темы/акцента и live reduced-motion preference обновляет поле, UI и previews через общий контекст без изменения state/seed/RNG/pause/ownership/history.
- Browser QA: 320×568, 397×752, 440×800, 956×340 и desktop; takeover не двигает поле, панель команд не зависит от игры, диалоги не перекрывают закреплённые действия.
- `bun run check` и `bun run build` проходят. Результат остаётся одним автономным HTML. Без коммита/пуша/публикации в рамках этой работы.

## Решение для согласования

Рекомендуется вариант 2: развить существующий картридж и Session до явного SDK, мигрировать обе игры и подтвердить расширяемость тестовым картриджем. До согласования этого контракта production-код не меняется. После согласования составляется проверяемый план реализации и выполняется миграция с отдельным финальным архитектурным ревью.
